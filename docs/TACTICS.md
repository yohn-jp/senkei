# 戦術言語・共通IR・Compute Units

## 1. 言語の目的（確定）

プレイヤーが、軍備・出撃・全軍戦略・レーン戦術・ユニットのエッジケースまで記述できる専用言語を用意します。条件分岐・状態変数・優先順位・関数的な再利用・ベクトル／行列処理のような集約操作を表現可能にします。

**ノーコードと生コードは同じ言語の二つの編集面**です。互いに独立した実装にせず、同じ意味論・命令集合・CU課金に収束させます。

## 2. 内部表現を正本とする（確定）

    No-code GUI ──┐
                  ├── Parser / Frontend ── Typed IR ── Validator ── VM
    Text DSL ─────┘

正本は構造化された型付き中間表現（Typed IR）です。テキストのASTは入力構文を解析する途中の表現であり、対戦時に信頼する実行契約ではありません。

- 明示型、作用域、シンボル、状態、操作、命令対象、優先順位、実行フェーズを表現する。
- 正規化と検証によって、任意の入力が同じ意味論に到達する。
- 型エラーや不正な操作は実行前に拒否する。
- UIとテキストから意味的に等価なプログラムを生成できることを検証する。
- 任意のテキストDSLをGUIへ戻す場合、GUIは高度な式を汎用ノードとして表現できる必要がある。不可逆な簡略化を行わない。
- IRのスキーマとシリアライズのバージョンを固定し、将来の移行を明示する。

テキストDSLの**名前、語彙、構文、キーワード、構文糖、具体的な型体系**は未決定です。サンプルの擬似コードは仕様ではありません。後続の独自言語設計で確定させます。

## 3. 必要な言語能力（確定）

| 領域 | 能力 |
| --- | --- |
| 観測 | 自軍・敵軍・レーン・施設・時間・イベント等、権限内の戦場状態 |
| 条件 | 比較、論理演算、複合条件、集合判定 |
| 状態 | 有限で型付けされた戦術メモリ、フェーズ、カウンタ、クールダウン |
| 選択 | if/else相当の条件分岐、優先度付きルール |
| 反復 | 有界な反復または等価な集合操作 |
| 集約 | ベクトル・行列・マスク・集計等のバッチ処理 |
| 行動 | 出撃、移動、撤退、増援、目標指定、リソース配分など定義済み命令 |
| 構造化 | 再利用可能な処理と、全軍／レーン／部隊／個体のスコープ |

表現可能な命令はゲームルールの公開する有限のCapabilityとして型検査します。敵の秘密状態の参照、ユニットの物理的に不可能な移動、存在しない予算の割当は許しません。

## 4. CU＝ゲーム内の計算資源（確定）

戦術の計算はゲーム内の有限資源です。プレイヤーは同じ軍備でも、効率的な戦術を低CUで実行することで高度な判断に余力を残せます。計算量の改善が競技上の利益となるのが設計意図です。

CUはホストCPU時間、WASM実行時間、JIT速度、実機のメモリ速度に連動させません。ルールとバージョン固定の論理的な操作料金で決まります。

CUの対象となる概念：観測／読取、比較・算術・集計、戦術状態の読書き、命令発行。実際の費用関数とTickごとの上限値は未決定です。

## 5. ベクトル化の意味（確定方向）

逐次の個別ループだけを唯一の表現にしません。選択マスク、集合比較、行列演算、集合への一括命令などを第一級の機能候補とします。

- 例：全兵士を走査して撤退させる代わりに、HP閾値マスクで一括選択する。
- ベクトル演算でも要素数に比例した仕事は消えない。安価にするならディスパッチ／制御オーバーヘッドや集約命令の意味論を明記する。
- 同じ処理をしただけで表層構文が違うことによる恣意的なCU差を作らない。
- コンパイラ最適化によるCU変化はプレイヤーが予測でき、版管理されること。ホストCPU依存の測定値をゲームCUにしない。

## 6. 予算と実行安全性

- 戦術はTick・試合等の定められた有限予算の中で評価する。
- 再帰／ループを導入する場合は上限・燃料を持ち、停止を保証する。
- 予算超過時の命令不発、フォールバック、状態反映可否はルールとして決定論的に定義する。
- 計算予算と兵力予算を独立の戦略資源として扱う。CUのレーン間配分やイベント時の集中は設計候補であり、固定数値ではない。
- 論理CUとホスト保護上のCPU時間・メモリ・バイト数・トレース容量の上限は別物。両方を設ける。
- 外部アクセスや任意のホスト言語コード実行を含めない。

## 7. コンパイラ・VM契約（確定原則）

1. 入力を解析・型検査し、構造化IRへ正規化する。
2. すべての作用域・利用可能データ・命令・コストを検証する。
3. 指定されたスナップショットに対して決定論的に戦術を評価する。
4. 必要なCUを精算し、命令を生成する。
5. 戦闘エンジンが競合命令をルールに従って解決する。
6. 条件評価、命令、CUの内訳をデバッグ可能なイベントとして記録する。

## 8. 言語設計の次の検討議題（未決定）

- 表層DSLの名前、語彙、宣言、式、ブロック、コレクション構文。
- 型：スカラー、ユニット参照、チーム、レーン、集合、マスク、行列、状態。
- スコープとイベント／Tickの評価タイミング。
- ベクトル化／行列演算とfor相当処理のCU比較の精密な定義。
- 命令集合・競合時の優先順位・状態更新の原子性。
- 静的CU見積もりと動的精算、最適化と計算資源の相関。
- 観測できる情報の粒度と、将来の攻守の非公開情報。
- GUIとテキストの往復可能性に関する仕様とコンフォーマンステスト。
