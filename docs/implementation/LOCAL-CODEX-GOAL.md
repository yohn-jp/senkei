# Local Codex — 正本実装と3D制作の統合Goal

## 1. Goalと今回の実行権限

`yohn-jp/senkei`の**定義済み正本の全実装・実動作検証**と、**12 Heroおよび必要な戦場アセットの採用品質への到達**を、1つのローカルCodex親セッションで完遂する。保存済み成果を引き継ぎ、計画・台帳・部品・PR作成だけで終えない。

本書はユーザーが指定した今回の実行契約であり、新しいゲームルールではない。旧指示の「Wave終了で停止」「別セッションのアート担当を待つ」「PRを出してユーザー／外部レビューを待つ」は撤回する。Waveは内部チェックポイントであり、完了後は同じGoal内の次の依存作業へ進む。

親はレビュー・検証・統合・commit・push・既存PR更新／mergeを行える。mainへの直接commitも許可される。**レビューを省略するのではなく、同一セッション内で完了させ、人間の個別承認待ちで停止しない。** 実際の権限・必須check・保護規則は迂回しない。

## 2. Authorityと未定義境界

最新のユーザー指示、本書の実行条件、採用済み正本と対象Issueの受入条件、適用されるリポジトリ規約、既存canonical implementationに従う。文書の責務と優先関係は `docs/README.md` を入口に確認する。Issue #5の実質的な品質条件を維持し、過去のPR #3専用ブランチ指示を今回の再開先にしない。

PR #22由来のUX-C01〜C16とUX-X01〜X08は、定義済み操作について今回のGoalに含む。文書に古い「将来」「合意案」が残っているだけで一括除外しない。一方、記載された候補・仮値・未決定・保留を確定仕様に昇格させない。監査・過去の検証記録は根拠であり、独立したゲーム正本ではない。

通常の実装判断（コンポーネント分割、既存APIとの接続、型、状態保持、ページング、フォーカス、エラー処理、テスト、既存画風内での具体造形）は自律的に進める。新しいゲーム意味論・経済条件・設計上の責務変更・基盤選定が必要な対象だけ `DECISION_REQUIRED` とし、独立作業は継続する。

未定義の装備倍率／ランク段階、ガチャ権利・確率・価格、Libra買取・回収、関係増加式・固有連携、研究・内政、オンライン権威、EOS／GS2採用、Production Behavior方針を捏造しない。共通機構や確定済み操作まで「未定義」にしない。有効なデータと処理が揃わない画面を本番の偽ボタン・仮報酬で埋めない。

## 3. 起動と保存済み成果の回収

[LOCAL-CODEX-HANDOFF.md](LOCAL-CODEX-HANDOFF.md)から再開する。ローカルの変更・既存worktreeを保全してoriginをfetchし、main、関連PR、各refの実HEAD、CI、規約を再取得する。引継ぎのSHAは照合点であってmainを巻き戻す指定ではない。

未マージ文書は `git show <ref>:<path>` またはそのrefのworktreeで読む。文書を読むためだけに未検証コードをmainへmergeしない。原本の圧縮証拠はmanifestのSHA-256／サイズを照合して復元する。旧 `/workspace/...` は説明用の出所であり、ローカルに存在する前提にしない。

初回にローカルCodexのversion、利用可能なsubagent機能、CPU／RAM／GPU、Rust/WASM、Node、ブラウザ、GitHub認証を確認し、現在の環境で実行できる経路を使う。ユーザーの全体設定・権限を勝手に緩めない。共有baselineの失敗は担当を一本化し、同じ調査を各Workerへ反復させない。

## 4. 単一親セッションと階層並列

親Coordinatorの下で、次の2系統を同時に進める。

| 系統 | 子タスクの分け方 | 集約責務 |
| --- | --- | --- |
| Product | Core／Behavior、UI／保存、契約Coverage、実ブラウザ受入の独立Leaf | 実データでつながる操作、現行mainの適合性 |
| Art | F01/R01と共通Generator、Rig／LOD、地形／施設、撮影・視覚検証の独立Leaf | 同一AppearanceとRendererでの採用品質 |

各系統のサブエージェントは、依存と所有範囲が分離できる場合にさらにサブエージェントへ委譲してよい。これは同じ親に管理されたagent treeであり、別ターミナル／別Cloudタスクの独立Coordinatorを追加する指示ではない。

ネストや同時実行の上限は実環境で確認する。子がspawnできない場合は親が同じLeafを直接spawnし、階層の制約だけで実装を停止しない。利用可能な機能がないのに並列実行したと報告しない。稼働数は全階層の合計で管理し、待機だけの階層や過剰な分割で枠を使い切らない。

### 書込みと統合の規則

- 書込みLeafは分離したworktree／branchを使う。1ファイルの編集権は同時に1担当だけ。worktree分離だけを競合対策とみなさない。親や系統担当も所有Leafのファイルを横から変更しない。
- `NextWorkspace.tsx`、`JourneyScreens.tsx`、`BattleAnalysis.tsx`、`HeroAtelier.tsx`、`JinreiWorkbench.tsx`の共有結線はProduct内の単一担当へ集約する。Renderer／Generatorの共有ファイルも単一担当。必要な修正は所有者へ返し、引渡しを記録する。
- 型・Schema・Snapshot・Worker境界のProducer/Consumerは実Symbolと版を先に照合する。変更を要する同じ境界を複数担当が独立設計しない。
- Leafは契約、base SHA、所有ファイル、依存、検証、成果commitを持つ。小さくレビュー可能な単位に分け、完了時は担当を解放する。目安の差分量を全Goalの停止条件にしない。
- 親だけが共有main／統合ブランチへのmerge・cherry-pick・pushとPR状態を管理する。Leafは割り当てられた専用branchだけを保存できる。無断force-push、破壊的reset、他担当の変更破棄は禁止。
- 親の統合は直列化するが、独立した制作・実装・レビュー・テストは並行する。保存済み依存commitの二重取り込みと旧ファイルの上書きを避ける。系統担当は自分の子成果を点検して親へ渡す。

ビルド・ブラウザのport、出力、trace、profile、Cargo target等も所有対象にする。異なるソースの同じ出力先を同時更新しない。workspace packageが別worktreeへ解決される共有node_modulesを使わない。共有可能なのは適合性・出所を確認した不変成果物と安全なcacheであり、古い成果物を新HEADの証拠へ転用しない。

重いNative/WASM buildは同じソースについて重複させない。Browser/GPUテストは実測負荷に応じて並列数を絞り、性能比較は競合負荷なしで測る。開始直後に両系統で実行可能なLeafを動かし、全台帳の再作成やCI待ちを前置条件にしない。

## 5. 実装とCoverageの完了単位

既存Coverageを再利用し、意味的な契約ごとに `Authority / 実装先 / 依存 / Owner / 状態 / 証拠SHA / 検証結果` を対応させる。2,682の原文単位を要件数や完成率にしない。重複統合と分類を必要な範囲から進め、最終的には全正本を覆う。既存の実装をゼロから作り直さない。

`DEFINED/MISSING`、`DEFINED/INCOMPLETE`、`DEFINED/VERIFIED`、`UNDEFINED/DEFERRED`と、実装済み／統合済み／検証済みを分ける。未配線のProducer、component harnessだけのPASS、未実行テストを実プレイヤー機能の完成にしない。新規台帳は必要最小限とし、親が一つの現行状態表を管理する。

保存済みの具体的欠陥と未結線を先に収束させながら、残る定義済み契約も順に実装する。既存PRの処理だけでGoal終了にしない。無関係なリファクタリング、先行抽象化、後方互換層、別シミュレータを作らない。

## 6. 3D制作の受入基準

PR #44のGenerator・文書・撮影基盤を再利用する。SophiaはSenkeiのHeroではなく対象外。F01/R01の再評価を先行し、両候補の合格後に残り10体へ展開する。地形・施設・検証基盤は並行して進める。既存役割・装備・画風からの具体造形は許可済みで、顔の個別資料がないことだけを停止理由にしない。新しい人物設定や未承認の武器置換は追加しない。

造形はFaceted Low-Poly、Pixel／Smoothは描画方式、Tactical／Cinematicは表示方針として分離する。展示と実Battlefieldは同じAppearance identityを使い、Enbu結果・Fog・CUを変更しない。

**Hard GateはIdentity、Geometry、Material、Animation、LOD、Integration、Determinism、Reproducibilityの全PASS。** 重大な欠陥や未検証を点数で相殺しない。共通生成規則、12体の部位別仕様、必須5動作、LOD、Manifest、実ゲーム統合まで対象にする。

合意済みの制作スコアをアート契約・評価表へ反映する。0=欠落／評価不能、1=重大破綻、2=目立つ欠陥、3=成立するが要改善、4=採用品質、5=基準を超える品質。Identity 30%、Silhouette/Proportion 25%、Geometry/Material 20%、Animation 15%、Tactical Readability 10%。**各Heroは加重平均4.0/5以上、全項目3.5/5以上**とする。全12体の平均で不合格Heroを隠さない。非Hero資産は該当する正本の個別受入で判定し、架空のHeroスコアを付けない。

固定視点・同条件の実画像／動作を、制作担当とは別のサブエージェントまたは親が実際に見て判定し、採点理由・欠陥位置・証拠SHAを残す。自己申告だけで昇格させず、ユーザーの逐次美術レビュー待ちは設けない。独立評価を実施できなければ未検証として保持する。

顔・衣装・接合、全動作周期と死亡終端、左右／背面／近景、全LOD、材質と画面サイズ別可読性、実戦の交戦・破壊・終局を検査する。欠陥を限定して修正→再撮影→再評価し、合格済みの特徴を保持する。反復回数だけで合格にせず、同じ欠陥が続く場合は原因を変えて調べる。旧画像、縮小contact sheet、静止pose、build成功だけで新HEADのVisual PASSを宣言しない。

## 7. レビュー・検証・公開を止めずにつなぐ

変更者以外のサブエージェント、または親が実diffと契約・周辺コード・テストを照合する。新たな外部レビュー依頼を待機ゲートにせず、指摘があれば同一セッション内で修正・再検証する。権限不足で統合できない場合も、独立した実装と検証は進める。

Focused TestをLeafで行い、親の統合HEADで必要な全体checkと実E2Eを行う。ローカルの `package.json`、Rust/WASM build、専用browser config、既存CIの正式コマンドを使う。テスト期待値の不整合は契約に照合し、失敗隠しのskip・範囲縮小・根拠のないtimeout増加はしない。

Desktop 1440×900／1920×1080、Mobile 390×844／430×932／幅320で、設計→実Enbu→Replay→分析→改善再戦→保存・復帰を検証する。Native/WASM、認可・Fog、変更不可Snapshot、保存失敗・import・Core再試行、アート統合の回帰を確認する。実ブラウザ、実GPU、物理端末、Visual、性能の判定を分ける。利用可能なローカルGPUで実測し、未接続実機を確認済みにしない。

CIは並走させ、待ち時間には独立Leafやローカル検証を進める。古いSHAのgreenや取消を新HEADのPASSにしない。ユーザー承認待ちは不要だが、必要な検証前に壊れたWIPをmainへ入れない。適合性を確認したまとまりは親がmainへ直接積むか既存PRをmergeし、統合後HEADを再確認する。

アートの未完了成果は原則として既存PR #44に集約し、Hero別PRを増やさない。今回の権限により合格後は親が統合できる。「以前はマージしない指示だった」という理由でレビュー待ち停止しない。他の既存PRも再利用し、依存差分を統合した場合は実状態に合わせて更新する。

## 8. 継続・保存・終了

Wave終了、PR作成、レビュー依頼、進捗報告、片系統の完了は終了条件ではない。親は同じ限定Goalの依存関係を更新し、次の実行可能Leafを起動する。未知の別製品や新規機能へ際限なく範囲を拡張しない。通常の実装判断・競合・テスト失敗は自律的に解く。

進捗は `契約／Asset → commit・統合先 → 検証 → 残件・次担当` を短く更新する。実装・証拠・引継ぎを節目ごとにcommit/pushし、ローカルだけの成果を溜めない。ユーザーの停止指示や実行容量の限界では、進行中プロセスを整理し、全Workerの変更と未追跡の必要成果を保存してremote HEADを照合する。秘密情報・cache・無関係なファイルを機械的に全addしない。

終了は、(A)両Goalの定義済み対象が統合・受入済み、(B)残件がすべて具体的な未決判断／利用不能環境に依存し独立作業もない、(C)ユーザー停止または実際の実行限界、のいずれかだけ。B/Cは部分完了として残件・根拠・再開点を保存し、未検証を除外してAへ言い換えない。存在しない自動再開・背景実行を約束しない。
