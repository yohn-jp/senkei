# UX-INTERACTION-CONTRACTS — 操作の意味・文脈保持・復帰と受入

## 1. 位置づけと合意範囲

本書は、既存のS00〜S15を横断する「操作で何が変わり、何が保持され、どこへ戻れるか」を具体化する**合意用の追加規範案**。文書PRの作成は合意・実装完了を意味しない。採用後は画面間の状態保持・操作結果の正本とする。

[PLAYER-JOURNEY.md](PLAYER-JOURNEY.md) は目的と開始条件、[PRE-BATTLE-FLOWS.md](PRE-BATTLE-FLOWS.md) は遷移、[PRE-BATTLE-SCREENS.md](PRE-BATTLE-SCREENS.md) は画面情報、[UI-DESIGN.md](UI-DESIGN.md) はDesktop／Mobileの表示契約を所有する。本書はゲーム数値、Jinrei文法、Enbu、観測権限を置き換えない。

装備・報酬・関係性の追加画面は [PROGRESSION-UX.md](PROGRESSION-UX.md) へ分離する。現在のG2に未実装の市場やガチャを暗黙追加しない。観測した不足と検証限界は [UX flow gap review](implementation/UX-FLOW-GAP-REVIEW.md) に記録し、仕様本文と混ぜない。

## 2. 操作文脈の不変条件（C01）

画面位置と対戦条件は別の状態である。以下は概念上の責務であり、新しいwire field名を強制するものではない。

| 文脈 | 含む情報 | 保持条件 |
| --- | --- | --- |
| 編集 | Draft identity／revision、5枠、Skill、Squad、Node、Jinrei | 閲覧・画面切替で内容を変更しない |
| 対戦 | Quick／Custom／Campaign、選択Scenarioと相手参照、RulePackage／World | 「確認」「戻る」で別の相手へ切り替えない |
| 分析 | Match／Experiment、観測視点、Tick、対象、イベント／診断参照 | Replay・Analysis・Editor間の移動で由来を保つ |
| ナビゲーション | 呼出元、戻り先、閲覧対象、フィルター、スクロール、フォーカス | 寄り道から実際の呼出元へ戻る |
| 保存 | 明示保存、Recovery、Completed Experiment、互換性 | 種類を区別し、閲覧を復元操作にしない |

「対戦条件を見る」はナビゲーションであって、Campaignを通常対戦へ変更する操作ではない。閲覧先の便宜的なモードをゲーム設定に兼用しない。実装方式として特定のrouterやstate libraryは指定しない。

## 3. Home・Quick・Campaignの開始（C02）

- S00ではCore／Catalog／保存領域の読込を別に示す。Core失敗を保存データ破損と表示しない。Coreが使えなくても可能な原データExport・Recoveryは残す。
- S01は「今のDraftで続ける」と「初期Presetへ置換する」を区別する。Quickの選択だけで作業中の戦型を初期化しない。
- S02は現在の対戦種別・Scenario・相手の公開可能な概要・利用可否・戻り先を表示する。Readyから確認に来た場合、変更しなければ同じ条件のReadyへ戻る。
- 同梱NPCもプレイヤーと同じCoreの合法性に従う。無効なNPCは「利用不可」と原因を表示し、別Scenarioへ戻れること。NPC側エラーを自軍のHero修正へ誘導しない。
- 訪問済み画面数ではなく実データの検証でReadyを決める。保存、ログイン、Coverageの完全証明は初戦の必須条件にしない。

## 4. Heroの閲覧と採用を分ける（C03）

S04→S05には、編成中Heroを調べる経路と、未採用の候補Heroを調べる経路の両方を設ける。**候補を見るために5枠の内容を変更させない。**

候補閲覧時は「閲覧中のHero」と「変更対象の枠」を区別し、明示的な採用操作でのみDraftを更新する。戻る／閉じるでは変更しない。詳細から採用する際は、置換する枠とSkill・Squad・Jinreiへの影響を示す。既存の即時採用ボタンを維持する場合も、読み取り専用の詳細入口を別に用意する。

S06のSkillは取得予定・現在の試合で取得済み・前提不足・別分岐を区別する。S07の分割→所属→共有Nodeは同じ5枠を使う。編成変更は無関係な枠を消さず、合法な値を保持し、失効の理由を示す。

## 5. Jinrei・Coverage・Preflight（C04）

S08のSource／No-code切替は同じ意味論の表現変更であり、表現できない内容を捨てて成功にしない。変換不可なら元の入力を残し、原因と継続可能な編集方法を示す。S09のNot Proven／Not Checkedをエラーや実測済みの保証へ変換しない。

S10の問題表示には少なくとも「どちらの陣営・何の対象」「原因」「修正可能な場所」「再検証する内容」を持たせる。未知の失敗を無理に特定Heroへ紐付けない。

| 問題の責務 | 修正／復帰先 |
| --- | --- |
| 自軍Hero・Skill・Squad・Node | S04／S06／S07の対象枠・項目 |
| 自軍Source・型・CU・参照 | S08の実Compiler位置。位置がなければ診断一覧 |
| 相手NPC・Scenario | S02の該当Scenario。不正な相手を直すため自軍を変えさせない |
| World／RulePackage／Catalog不一致 | S15。原データを保持して版の差異を表示 |
| 実行環境の障害 | S15／S10。原因に対応した再試行 |

単に4画面への一般リンクを並べただけで、対象付きの修正導線を満たしたと判定しない。

## 6. 長い処理と中断・復帰（C05）

Compile／Preflight／Enbu／Import／Saveは、対象・処理中・成功・失敗を区別する。実測していない進捗率や残り時間を作らない。二重開始と、古い処理応答による新しいDraft／Runの上書きを防ぐ。

実行中の閲覧移動を認めるなら進行状態へ戻れる入口を保ち、認めないなら理由を示す。画面から離れただけで取消済みとは表示しない。取消機能を提供する場合はCore／Workerの停止・無効化が確認できて初めて取消完了とする。対応しない状態に動かない取消ボタンを置かない。

Core再読込・再試行が必要でも、編集中Draft・既存Run・保存原本を保持する。遅延／不明な状態を勝利・保存成功・報酬付与として扱わない。

## 7. Replayから原因と修正先へ（C06・C07）

1. S12でTick・可視対象・イベントを選ぶ。
2. S13へ移ると、同じMatch・視点・Tick・対象を初期の分析文脈として使う。全試合の先頭へ戻すだけでは接続にならない。
3. 対応する認可済みObservation／Decision Traceを調べる。記録がない、未取得、非公開、対応不明を区別する。
4. 実際に対応するAction／Scope／Source位置を解決できる場合だけS08へ移動する。Program digestが現在Draftと違う場合は、元Runの根拠と現在編集を区別して表示する。
5. 編集後も、根拠になった元の分析箇所へ戻れる。過去のSourceを現在Draftへ無断で上書きしない。

**全ての提供済み診断へ到達できること。** 最初の60件等だけを表示して残りへの操作がない状態は不可。Tick／対象の絞込、ページ分割、区間表示等で負荷を抑えてよい。Producer側で打ち切られた場合は取得範囲を示し、存在しない後半を補完しない。

発生イベントと「原因」は同義ではない。推測、観測事実、採用／拒否の診断を表示上も分ける。フォグから消えた敵を分析リンクや発話で現在位置Knownへ戻さない。

## 8. 再戦と比較の三種類（C08）

| 操作 | 入力 | 表示する意味 |
| --- | --- | --- |
| 元の試合を再実行 | 不変Run Snapshotを再検証 | 完全に同じ試合条件。現在Draftは保持 |
| 改良した戦型を比較 | 変更対象以外の条件を基準Runに固定 | 戦術改善の比較。何を変えたか明示 |
| 新しい条件で対戦 | 現在の対戦選択とDraft | 相手・World等が違えば参考比較 |

同じMatch IDだけで同条件と判定せず、異なるMatch IDだけで意味的な条件差とも判定しない。Snapshot、World／Ruleset、相手Program・構成・初期状態、上限・実行版など、結果を変える入力を照合する。変更対象にしていない相手や初期条件が違うなら「同条件で改善した」と断定しない。

差分の比較対象を明示する。今回のPRは実験保存件数を増やす判断ではなく、既存の最新／直前Runでも、比較できる範囲とできない範囲を正しく伝える契約である。

## 9. 保存・Import・復元（C09・C10）

- 明示保存したSetupと現在Draftの比較は、実際の保存対象を漏れなく含む。Scenario／相手参照が変われば、Hero・Sourceが同じでも変更済みと表示する。
- 「Recoveryへ自動保存済み」と「明示保存と一致」は異なる。Completed Experimentの保存成功とも混同しない。
- Libraryは明示保存・Recovery・最新／直前Experiment・旧形式保全を別の対象として示す。履歴が無制限に残るように見せない。
- 最新2件が保持範囲なら、通常画面で範囲・置換タイミング・Export手段を説明する。削除確認画面にだけ件数を記すのでは不十分。
- Restore／Importで現在の異なるDraftを置換する場合、置換対象と差異を確認でき、取消・事前Exportまたは保全を選べること。既に同一内容なら無意味な確認を増やさない。
- Importは検証成功前に元の保存物を消さない。形式、容量、互換性、読み取り不能を区別する。
- 不一致データは原データをExportできる状態に保つ。「対応版を読み込む」操作が未提供なら、存在する解決ボタンのように誘導しない。
- Exportはファイル生成・ダウンロード開始と、端末側への保存完了を区別する。確認できない端末保存を成功保証しない。

## 10. Campaignの進行と戦後の次の操作（C11）

ロック中、解放済み未攻略、攻略済み、現在選択、最終課題完了を区別する。数値の「解放件数」だけでは攻略履歴を表さない。課題の見どころと、実際に判定する勝利条件は別に表示する。

勝利後は、次の解放課題へ準備する、同じ課題を改善する、結果を見る、Homeへ戻る、の意味を分ける。最後の課題では完了と再挑戦先を示し、存在しない「次へ」を表示しない。敗北・Draw・実行失敗で、未達をクリアにしない。

今回の合意案は進行表示と導線の不足を埋めるもので、報酬確率・解放条件・勝敗数値を追加しない。ガチャ等の将来報酬は別の有効化された定義がない限り表示・付与しない。

## 11. Desktop・Mobile・戻る操作（C12）

同じ論理Screenとデータでも、Mobileは独立した作業面とする。主要操作を横Tabのスクロール・ピンチ・ドラッグだけに依存させない。

戻る操作は「Sheetを閉じる→呼出元の作業面→入口」の関係を明示し、現在のDraftや対戦条件を暗黙変更しない。ブラウザの戻る／進むをアプリ内遷移に対応させる範囲は実装で明記し、対応する遷移ではアプリ内Backと同じデータ保持を満たす。履歴を装ってページ外へ意図せず退出させない。

Sheet／Dialogには名前、閉じる操作、キーボードの到達経路を持たせ、開いた元へフォーカスを戻す。モーダルとして宣言するなら背景操作もその宣言と一致させる。320px、端末回転、Safe Area、IME表示時も修正・保存・戻るが使えること。これはコード検査やスクリーンショットのみで実機PASSにしない。

## 12. 操作単位の受入シナリオ

以下のテストIDは受入要件であり、テストが存在・実行済みという主張ではない。元のUX-ENTRY等の受入を置換せず補完する。

| ID | 操作列 | 確認する結果 |
| --- | --- | --- |
| UX-C01 | Campaign選択→Ready→条件を見る→戻る | 相手・Scenario・Draftが同じ。閲覧だけなら失効しない |
| UX-C02 | 全同梱NPCを選択→CoreでPreflight | 合法NPCのみ開始可能。不正NPCの原因は相手側として表示 |
| UX-C03 | 未採用Hero詳細→戻る→同じHeroを明示採用 | 閲覧は無変更、採用時だけ対象枠と関連検証が変化 |
| UX-C04 | Skill／Squad／Sourceを変更→Ready問題→修正→復帰 | 対象付きの原因・修正リンク。無関係な設定は保持 |
| UX-C05 | 長い実行→閲覧／再試行／提供される取消 | 二重実行・古い応答の上書きなし。結果不明は成功にしない |
| UX-C06 | 後半Tickのイベント→Analysis→該当Trace→Replay | 同じMatch・Tick・対象、60件超でも提供済み記録へ到達 |
