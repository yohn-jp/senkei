# Senkei / Jinrei / Senritsu / Enbu — 名称と責務の正本

## 1. 確定した名称

| 名称 | 表記 | 意味 | 第一義 |
| --- | --- | --- | --- |
| **Senkei** | 戦型 | プレイヤーが設計する戦型、およびそのゲーム／制作環境 | 製品・戦型アーティファクト |
| **Jinrei** | 陣令 | 戦型を動かす指示・判断 | 戦術DSL・型検査・コンパイラ・戦術VM |
| **Senritsu** | 戦律 | 戦型同士が従う法則 | バージョン付きゲームルールセット・ドメインスキーマ |
| **Enbu** | 演武 | 二つの戦型を規則に従って実演・競わせる | 汎用の決定論的シミュレーション・オーケストレータ |

「Senkei」はゲームのブランドだけでなく戦型そのものの名称でもある。「Enbu」は**Senkei戦闘ルール固有の戦争シミュレーター**ではなく、型（戦型）をルールに従って実行するエンジンである。

- **確定**: これら四つの名称と、エンジン／ルールセット／戦術言語を分離する責務。
- **設計方針**: 以下の依存・インターフェースの方向性。
- **未決定**: 公開パッケージ名、具体的な構造体名、シリアライズ形式、CU単価、個々のルール数値（Jinreiの表層文法v0.1は確定済み）。

## 2. コンポーネント境界

```text
                       Senkei (戦型 / product)
         ┌────────────────────┴─────────────────────┐
         │                                          │
  Combatant A                                 Combatant B
  army / placement / strategy                army / placement / strategy
         │                                          │
         └────────────────────┬─────────────────────┘
                              │  immutable, validated snapshots
                       ┌──────▼───────┐
  Senritsu package ───►│     Enbu     │────► MatchResult
  rules / schemas       │ simulation   │────► PresentationReplay
  effect definitions    │ orchestrator │────► RestrictedDiagnostics
                       └──────┬───────┘
                              │ TacticalExecutionPort
                       ┌──────▼───────┐
                       │    Jinrei    │
                       │ verified VM  │
                       └──────────────┘

  Jinrei source/no-code → compiler + Senritsu schema → typed/costed IR
                                         → validated bytecode → combatant
```

- **Senkei**: 兵科・数・配置・生産／出撃方針・戦術プログラムの参照・初期メモリ・対象の戦律バージョン等を束ねる。不変スナップショットを対戦へ提出する。ストレージ・編集UIそのものは製品アダプターであり、データモデルとは区別する。
- **Jinrei**: プレイヤー戦術を型検査、正規化、論理CU付与、専用バイトコード化し、**戦闘中は観測と戦術メモリを入力して命令候補（Intent）と次状態を返す**。ワールドを直接変更しない。
- **Senritsu**: 世界の型・能力・制約・数値、観測可能な情報、命令の意味、戦闘の遷移規則、勝敗条件、CU料金表、公開可能なイベント種別を宣言・構成する。
- **Enbu**: 戦律の妥当性・バージョンを検証し、戦闘状態とTickを管理し、同じスナップショットを両陣営へ提示してJinrei VMを呼び、命令調停・規則適用・決定論的な終局判定・リプレイ生成を行う。ネットワーク、課金、認証、ランキング、描画は含めない。

EnbuはJinreiの**コンパイラ・ソース構文**を知る必要がない。戦術の実行結果を得るための型付き実行ポートだけに依存する。JinreiはEnbu内部構造を参照せず、Senritsu由来の観測スキーマとCapability契約を使う。SenritsuにはEnbuの内部状態ポインタや任意のホストコールバックを渡さない。

## 3. 拡張性の境界

ゲーム内の三つのレーン、歩兵・騎兵、塔、本拠地、出撃コストは**最初のSenritsu**が持つ。Jinreiの予約語やEnbuの固有データ構造として固定しない。

ただし完全な任意ルールの万能エンジンは目指さない。Enbuが提供する**バージョン付き・有限の遷移プリミティブ**で表現可能な範囲に限り、Senritsuの交換だけでルールを追加できる。新しい種類の物理計算・状態遷移が必要な場合は、Enbuのプリミティブと互換性契約を意図的に拡張する。

拡張には下記の段階がある。

1. 数値・兵科・初期配置・勝利閾値の変更: Senritsuのデータ更新。
2. 既存プリミティブの新しい組み合わせ: Senritsuのルール更新。
3. 新しい観測・Command/Capability: Senritsuの型付き定義と必要な実行ポート拡張、Jinreiの再検証。
4. 新しい遷移の意味論: Enbuのプリミティブ・契約・検証を新バージョンとして追加。

## 4. 権威と版管理

- Senritsuは安定した`ruleset_id`、意味論バージョン、**コンテンツダイジェスト**で識別する。版番号だけで実体を推測しない。
- Senkeiは対象Senritsuの識別子・ダイジェスト、軍備・配置、Jinreiのプログラム版・CU版を記録する。
- Jinreiの型検査・命令合法性は対応するSenritsuスキーマを使う。
- Enbuは互換性のあるSenritsu、Jinreiバイトコード版、CU版、エンジン版のみ受け入れる。
- リプレイには全入力の識別情報を残す。完全再計算にはハッシュではなく保護されたスナップショット実体が必要。
- ゲーム内論理CUとホスト物理時間の分離を維持する。

## 5. 許されない責務の混同

- JinreiコードからゲームのHPや資源を直接変更する。
- Senritsuから任意JavaScriptや任意Rustプラグインをロードしてルール定義と称する。
- Enbuの中に初期ゲーム専用の兵科や3レーンをハードコードして汎用性を装う。
- 公開リプレイに相手の戦術コード・IR・秘密状態・CU実行トレースを含める。
- ブラウザの計算結果を将来の公式戦の信頼済み結果として扱う。
