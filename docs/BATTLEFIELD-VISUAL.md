# Battlefield Visual — 3D戦場のデザイン・受入正本

## 1. Goalとauthority

**目的は実際のBattlefieldを、観察・理解・鑑賞できるStylized 3D Tactical Fantasyとして完成させること。** モック、平面トポロジー図、ラベル付きの仮ジオメトリは納品物ではない。

- ゲームの接続・距離・移動・橋・交戦は [BATTLEFIELD.md](BATTLEFIELD.md) が正本。本書は**視覚構成・造形・操作・視覚受入**の正本。
- 共通の画風は [GRAPHICS.md](GRAPHICS.md)、Hero identityとLODは [HERO-ATELIER.md](HERO-ATELIER.md)、UIは [UI-DESIGN.md](UI-DESIGN.md)、観測・秘匿は [REPLAY.md](REPLAY.md) に従う。
- **実Jinrei → Enbu → 認可済みPresentationReplay → Three.js**の試合を対象とする。Pixel 3Dは任意の表示方式であり、造形不足を隠す方法ではない。
- [PR #7の実画面](https://github.com/yohn-jp/senkei/blob/6fa8296de8c3f85a50b064012f5a0bf3b891600e/docs/evidence/battlefield/canonical-browser/desktop-1440x900-bridge-destroyed.png)と[モバイル画面](https://github.com/yohn-jp/senkei/blob/6fa8296de8c3f85a50b064012f5a0bf3b891600e/docs/evidence/battlefield/canonical-default/mobile-390x844-t016.png)を**未達の比較元**とする。実戦WASMは接続されているが、三レーンの密集、地形・建築の簡素さ、ラベルによる戦闘遮蔽が残っている。

## 2. マップの地理・空間（必須）

1. **三本の独立した戦闘回廊**：対角のA/B本拠地、TOP/MID/BOTの進軍路を十分に離して配置する。標準Overviewで三レーンが一本の帯に潰れず、地名やミニマップなしで追えること。現在の密集した視覚座標は再設計対象。
2. **二つの立体ジャングル**：TOP–MID、MID–BOTの間に森林の体積・起伏・岩場・開口・一本の通路を持つ独立領域を作る。道の線＋樹木の点描は不可。4キャンプは枝道終端の開けた広場として造形する。
3. **斜めに横断する一本の川**：TOP側からBOT側へ連続した水系。水面・河床・岸・高低差・浅瀬を立体化する。川を単なる青い帯で表現しない。
4. **固定橋3サイト**：TOP/MID/BOTの位置のみ。通常橋はCENTERだけ、拡張橋はLEFT/RIGHTも通れる。破壊後は徒歩渡河。橋脚・床板・欄干・損傷形状によって、状態をラベルなしで区別できること。
5. **ジャングル渡河2地点**：橋を架けず、河岸・浅瀬・渡河口として表現する。道の帯を水面上に残し、架空の橋があるように見せない。
6. **MID河上観測基地**：橋のマーカーではなく、独立した広場・基礎・防壁・観測塔／ビーコンを持つ河上建築。両岸から連絡橋でアクセスする。占拠・争奪・観測の状態は実Replayに連動し、旗・灯火等で読める。
7. **ノードと3トラック**：通常ノードは広場、塔は防衛建築、本拠地は大拠点。レーンには幅があり、MinionのCENTER進軍とHeroのLEFT/RIGHT位置、横断、橋への合流が追跡視点で分かる。線を3本引くだけでは不可。

### Worldとの境界

- **35ノード／42エッジ、接続、論理距離、橋・渡河の固定地点は変更しない**。宣言的World CompilerとLogic/PresentationのDigest・責務分離は [WORLD-DEFINITION.md](WORLD-DEFINITION.md) に従う。視覚用の座標埋め込み・曲線・高低差・道路幅は改善可能だが、経路探索・移動Tick・射程を暗黙に変更しない。
- 再配置する場合はWorld側の座標とReplay投影を整合させる。Rendererだけに独立した偽マップを作らない。見た目の交差点や装飾路から新しいエッジを作らない。

## 3. 3D造形とHero（必須）

- **地形**：連続した起伏、道と広場の段差、河岸の断面、樹冠高低差、岩・草・低木の粗密を実形状で構築する。単一平面＋ノイズ色＋均一な樹木散布では不可。
- **建築**：本拠地、塔、橋、観測基地、キャンプを基礎・壁・屋根・柱・旗・損傷など意味ある形状で作り分ける。役割と所属を形でも識別できること。
- **材質**：石・土・木・水・金属・布の一貫したStylized 3D材質、光と影。Smooth 3Dでも成立し、Pixel 3D切替でも輪郭が読めること。
- **Hero**：兵科、装備、武器、姿勢をシルエットで区別できる戦場モデルを用い、箱／円錐の仮人形を完成扱いしない。Hero Atelierと同じidentity・材質系列からLODを派生させる。[F01の静的研究](F01-PROCEDURAL-STUDY.md)は**未承認の実験**であり、そのまま本番モデルとみなさず、動作・LOD・描画統合を検証する。
- **Minion/Monster**：Heroと異なる輪郭・装備・サイズ体系を持つ。多数体はInstancing/LODで最適化してよいが、識別不能な点群にしない。
- **演出**：進軍、停止攻撃、被弾、Skill、撤退、橋破壊／再建、渡河、基地争奪を確定Replayに同期した異なる動き・短い効果で示す。移動攻撃や存在しないヒットを演出しない。

## 4. カメラ・情報階層・Mobile

- **Desktop Tactical（初期）**：戦線と交戦位置を見られる主画角。全地図を無条件に詰め込んでHeroを点にしない。**Overview**は全レーン・ジャングル・河川・拠点の地理を示す別視点。**Follow**は装備、位置取り、攻撃、渡河を見せつつ前方の危険も読める視点。
- **Mobileは独立レイアウト**：戦場を主役とし、再生／停止・シーク・速度・Overview・Follow・Details・Timelineを操作できる。Desktopの縮小は禁止。詳細はタップで開くパネルへ分離し、閉じた後もTick・選択・カメラを保持する。
- **第1視線は戦場とUnit**、第2視線は選択状態・Tick・操作、第3視線はイベント文章・診断。攻撃・ダメージの黒いカードを画面中央へ積み重ねて戦闘を隠さない。対象の短いCue＋Timeline/Detailsに置き換える。
- 地名・施設名は重なり回避・ズーム段階・選択時展開を使う。ラベルで地形や施設の造形不足を補わない。Unknownは可視化で推測補完しない。

## 5. 受入シナリオ（実画面必須）

全地理探索済みの**認可されたテストView**で造形全体を検証することと、実試合Overviewで未探索地形や未観測の敵・橋の現在状態を明かすことは別である。表示モードは[ART-DIRECTION.md](ART-DIRECTION.md)、Fogは[FOG-OF-WAR.md](FOG-OF-WAR.md)に従う。

| シーン | 目視で成立すべき状態 |
| --- | --- |
| Overview初期 | 3レーン・2ジャングル・4キャンプ・斜行河川・橋3・渡河2・河上MID基地・両本拠地を識別できる |
| Tactical交戦 | Hero/Minion、戦線、停止攻撃・被弾がラベルに隠れず読める |
| Follow Hero | 兵科・装備・移動／攻撃の違い・前方の地形が見える |
| Lane横断 | LEFT/RIGHT、CENTER補給、Hero横断とMinion占有が分かる |
| 橋の状態 | 通常／拡張／破壊／徒歩渡河の建築差と通行が分かる |
| JungleとNode | 森の通路、キャンプ広場、橋なし渡河、ノードでの集団戦が分かる |
| Mobile実戦 | 戦場が主役で、再生・選択・Details/Timeline往復が実操作できる |

**検証契約**：
1. PR #7のBefore画像と**同条件のAfter画像**を比較する。色・ズーム・文字変更だけでなく、レーン間隔、地形の体積、基地・橋の造形、Heroの識別、ラベル重なりを実際に改善する。
2. 提出HEADの**本番ビルド＋実Jinrei/Enbu/WASMの試合**で、初期／交戦／横断／橋の通常・拡張・破壊／徒歩渡河／基地争奪／終局を、Tactical/Overview/Followで確認する。Fixtureだけの成功は禁止。
3. Desktop 1440×900・1920×1080、Mobile 390×844・430×932・320pxで撮影・操作確認。Pixel/Smooth切替、再生・シーク・カメラ・選択・Detailsを検証する。各証拠にHEAD SHA・Tick・Viewport・カメラを紐づける。
4. **Functional / Visual / Interaction / CIを別判定**する。スクリーンショットの存在やgreen CIだけで美観をPASSとしない。明確な視覚未達があればPRをReadyにしない。物理GPU・実機タッチ等の未実施はNOT_CHECKEDとする。

## 6. 実装境界

- PR #7の実Enbu/Replay接続と既存のゲームルールは維持する。視覚修正を口実にJinrei文法、戦闘数値、勝敗計算、権限を変えない。
- 新しい偽データ・別レンダラー・スクリーンショット専用の描画経路を作らない。既存のThree.jsとReplay契約に統合する。
- モックで一度見せることは制作過程として可能だが、**本番実戦画面で成立しない限り未完成**と報告する。
