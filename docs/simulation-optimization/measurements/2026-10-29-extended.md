# Senrei scheduling research — 14ケース × 7方式 実測と分析

> **観測済み / 合成実験 / Enbu本番未検証**。この結果はNode.jsで実装した独立した簡略化戦闘モデルの実行時間であり、Rust Enbu / Jinrei VM / Senritsuの高速化率ではない。前回の独立ユニットのみの実験に対し、共有ターゲットへの**同Tick同時ダメージ**、周期的可視性、スポーン時間差、死亡後の停止を追加した。

## 1. 対象モデル・手法と検証

- 各主体は初期位置から定速で到着点へ移動し、到着した**次のTick**から攻撃可能。各ターゲットには共有HPがある。各Tickの全攻撃は開始時点のHPを参照し、合計ダメージを**同時コミット**する。攻撃後にターゲットが死亡しても同Tickの他の攻撃は成立する。
- 視認可否はターゲットごとの周期関数 \(V(t) = (t\bmod P)<W\)（説明上の論理ゲートであり、本物のJinrei Fog/Unknownではない）。隠れている間は攻撃できず、次の可視Tickで発火する。Spawn時刻、速度、攻撃間隔、対象HP、攻撃力は整数。
- **全Tick / Active Set / Binary Heap / 時間Bucket / 周期閉形式 / 局所Hybrid / 二層Adaptive** を、同じ意味状態と攻撃時刻列へ正規化して比較。
- 固定14シナリオ×5主体数×8Tick上限 = **560組**、加えて決定的疑似乱数による**200組**。全候補6方式に対して全Tick基準との最終位置・ターゲットHP・次攻撃Tick・発射件数・発射Tick総和・**全攻撃Tick列**の一致を確認（760組×6＝4,560比較）。
- Numeric semanticsはこのモデルで安全なJavaScript Number整数範囲のみに限定。Senritsuの飽和/オーバーフローは未検証。

## 2. 測定条件

- 実行環境：v22.16.0 / Linux x64 / AMD EPYC 9V74 80-Core Processor（見えている論理CPU数 5）。性能評価は一つのNodeプロセスで逐次実行。
- 「Result-only」は各主体の最終状態と攻撃件数・時刻総和を計算（個々の攻撃イベント配列を生成しない）。「Attack timeline」は**全攻撃Tick列を物理的に生成**。これは全TickのWorld Snapshot/Replayを生成するテストではない。
- Result-only: 256主体×2,000Tick（warm-up=2, samples=5）の7方式、および512主体×6,000Tick（warm-up=3, samples=7）の6方式（*二層Adaptiveは大規模側未計測*）。
- Attack timeline: 256主体×2,000Tick（warm-up=2, samples=5）、7方式。
- 下表は**中央値 [ms/1戦闘]**。サンプルごとのp95/min/maxとバッチ係数は圧縮保存した計測JSONに残している。実行入力のコピー・正誤照合は計時外。短時間処理は最大48回のバッチ平均を使用。JIT/GC/CPUクロックなどの揺らぎを排除した保証はない。
- 試行間・異なる計測ランの数値を直接1行として比較しない。各表の一つの規模・出力モード内で比較する。

## 6. 主要な結果

1. **一律の方式は敗北する**。大規模Result-only（512×6,000）では最速方式が周期式6、Active 4、Heap 2、局所Hybrid 2ケースに分散した。Hybridでさえケースごとに単独方式に負けており、現行の推定コスト式はまだ十分ではない。
2. **攻撃イベントが密集するとイベントキューは破綻し得る**。大規模の`dense_hits`では全Tick 22.573 ms、Heap 337.687 ms、周期式 0.116 ms。周期式は各打撃を列挙せず、攻撃回数・時刻和を直接求める。密な場面ではHeap/Calendarなど単体のイベントスケジューラで最適化を完結させない。
3. **即死/早期勝敗ではActive Setが強い**。大規模の`shared_small`では Active 0.012 ms、周期式 0.526 ms、局所Hybrid 0.022 ms。二分探索と式/グループ生成より、数Tickで終わる逐次処理の方が軽い。
4. **長距離移動には到着時刻予測**。大規模の`long_travel`ではHeap 0.008 msに対し全Tick 11.228 ms、Active 18.197 ms。全主体はホライズン中に攻撃せず、移動状態の直接計算が効いている。二層Adaptiveでは「到着しない」という証明からキュー自体を作らない案を追加。
5. **視認の周期性も解析できる**。周期内の攻撃可能位相を有限状態として構築し、繰返し周期を飛ばしたうえで、累積与ダメージがHPを超える最初のTickを二分探索する。大規模の`fog_rapid`では周期式0.113 ms、Heap139.177 ms。
6. **出力の物理生成が別の下限**。256主体×2,000Tickの`dense_hits`は**427,000件の攻撃**。周期式はResult-onlyで0.023 ms、全攻撃時刻列生成では22.700 ms。閉形式で計算を省けても、要求されたイベントを列挙する費用は消えない。もちろん本物のFog/Public/Owner Replayを対象にした測定ではない。
7. **二層Adaptiveはまだ万能ではない**。同型群を誤分類すると、最速の周期式に対して計画選択や無駄なActor走査の費用が発生する。特徴量に「時間ホライズン、最初の攻撃時刻、死亡時刻の粗い上界、グループ数、出力件数、視界の周期性」を追加し、オンライン自動切替より先にオフラインでコストモデルを調整する。

## 7. 新しく実装した数理手法

### P1: 周期可視性を有限状態の位相遷移として解く（`periodic`）

攻撃時刻を `a[0]=first_visible(first_attack)`、`a[i+1]=first_visible(a[i]+interval)` とする。位相 `a[i] mod period` は有限集合であるため、必ず周期に入る。周期開始までのprefix、周期内の攻撃時刻、周期の長さ・時間幅を保存すると、任意Tまでの攻撃回数・時刻総和を式で計算できる。

共有ターゲットHPについて `D(T)=sum_i damage_i*hits_i(T)` は（ダメージ非負の本モデルでは）単調なので、`D(T)>=initialHP` となる最初のTickを二分探索し、同Tickに成立したすべての攻撃を計上する。周期の外側の別効果がこの関数を変える場合は区間分割かfallbackが必要。

### P2: 最初の一斉攻撃だけで死亡するか直接判定（`hybrid`）

各Actorの初回可視攻撃Tickの最小値 `t0` を求め、同Tickの合計ダメージがHP以上なら、そのTickの攻撃だけをコミットして終了。二分探索/周期構築/イベントキューをすべて回避する。判定自体は線形の費用を持つため、閾値選択を含め比較する。

### P3: 共有ターゲットごとの計画選択（`hybrid`）

単一の全試合キューではなく、ターゲット単位に `firstVolleyKill` / `eventGroup` / `periodicGroup` を割り当てる。独立したターゲット間の依存がないモデルに限る。本番ではSCCやFogの共有依存も分割境界へ加える必要がある。

### P4: 全体分類→局所分類の二層選択（`adaptive`）

全試合で攻撃機会がなければ位置を一括計算。全員既到着で小HPならActive Set、移動後の短期攻撃ならHeap、その他は局所Hybridへ振り分ける**検証用ヒューリスティック**。性能の最適化はまだ未完了。
