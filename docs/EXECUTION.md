# コンパイル・実行・データ境界

## 1. 目的と確定事項

この文書は戦術言語のコンパイル、論理CU、戦闘エンジンの実行形式、結果出力に関する合意済みのアーキテクチャ契約を定義する。Jinreiの表層文法、観測／Truth型と論理評価順序は [JINREI-GRAMMAR.md](JINREI-GRAMMAR.md) で確定済み。本書ではSenritsu固有のDomain型・CU単価を固定しない。

- Jinrei（陣令）は**コンパイル型DSL**。人が記述した戦術を直接JavaScript/Rustなどの任意コードとして実行しない。
- コンパイルした戦術は、検証可能な**専用バイトコード**としてRust製の**Jinrei VM**が実行する。
- Jinrei VM・コンパイラ・EnbuエンジンはRust製で、ブラウザ配布時に**WASMバイナリ**へコンパイルする。プレイヤーの戦術を毎回WASMへコンパイルするわけではない。
- ゲーム内CUは論理的な計算資源。実際のCPU時間、WASM命令数、メモリ帯域、JIT、SIMD、ホスト性能と切り離す。
- Enbuは双方の戦型と検証済みSenritsu・戦場の確定スナップショットを受け、勝敗・統計・描画用リプレイを計算して返す。描画、アカウント、DB、レーティング、チケットは担当しない。

## 2. コンパイルパイプライン

    Text DSL → Parse AST ──────────────┐
                                      ├→ Typed Semantic IR
    Visual Editor → Structured AST ───┘       │
                                              ↓
                                     Validator / Normalizer
                                              │
                                              ↓
                                      Costed Logical IR
                                      (CU semantics fixed)
                                              │
                                              ↓
                                     Optimizer / Lowering
                                     (CU-preserving only)
                                              │
                                              ↓
                                       Tactical Bytecode
                                              │
                                              ↓
                                     Jinrei VM (written in Rust)
                                      ├─ Native binary
                                      └─ WASM binary (browser)

ノーコードとコードで等価の戦術を構築した場合、等価の正規化IR、CU意味論および戦闘結果へ収束させる。正本はパース時のASTではなく、型と意味を検証した構造化IR。GUIは任意の合法IRを汎用ノードとして損失なく表現できることを目標にする。

Typed Semantic IRは「何を計算するか」を表す。Costed Logical IRは、計算対象・条件・評価回数とCU課金可能な論理演算を確定する。専用バイトコードはその契約を実行する形式であり、WASMバイナリとは別物。Senritsuは独立した不変のルールパッケージとしてDomain SchemaとCapability/CU契約をJinreiに提供する。Enbuは検証済みRulePlanを解決して、Jinrei VMから返された命令候補を規則に沿って適用する。責務の正本は [COMPONENTS.md](COMPONENTS.md)。

## 3. 論理CUと物理最適化の隔離

### 3.1 計算契約

- CUはCosted Logical IR上のバージョン管理された**論理操作**と、実際に評価された論理上の要素数・分岐に基づく。
- 計算対象には戦場の観測、比較・算術、選択／集約、戦術メモリの読書き、命令発行がある。
- 評価されなかった論理演算は課金しない。通常AND/ORと集合量化は全要素を論理的に評価し、短絡によるCU削減はJinreiの明示的な `ordered and/or` に限る。詳細は [JINREI-GRAMMAR.md](JINREI-GRAMMAR.md)。
- UIの表現形式・テキストの長さ・物理時間ではCUを変えない。
- CUスケジュールはルールと独立に識別可能なバージョンを持つ。

### 3.2 二種類の最適化

1. **プレイヤーが明示的に行う論理最適化**：集約、再利用する状態、評価間隔、対象選択、発行命令数を変え、課金対象の論理操作が減ればCUも減る。
2. **ランタイムが行う物理最適化**：SIMD、命令融合、レイアウト変更、キャッシュ、冗長な物理ロードの除去、JIT等によって実時間を短縮する。ただし、Costed Logical IRが規定する**結果・状態遷移・論理CU・公開された論理トレースを変えない**。

同じ論理観測を2回要求する戦術をVMが内部キャッシュで1回の物理ロードに畳み込んでも、CU上は2回の要求として課金される。プレイヤーが明示的に値を保持・再利用し、論理的要求を1回に減らした場合は、定義に従ってCUが減り得る。

コンパイラによる共通部分式除去などの最適化は、論理CUイベントを消さずに物理実行だけを変えるか、ルール版で明示された**課金前の正規化**として扱う。意図しないコンパイラのバージョン更新で既存戦術のCUを変更してはならない。

ベクトル・行列操作は第一級の論理操作だが、内部要素処理を無条件に定数時間・定数CUとみなさない。セットアップ・対象数・集約・個別ディスパッチなどの費用関数を後続で定義する。

### 3.3 安全性との切り分け

ゲームCUとは別に、実行環境保護のためCPU時間・メモリ・入力サイズ・最大Tick・最大イベント数の上限を設ける。CUが上限以内であっても、ホスト保護上限を超えたジョブは安全に停止できるようにする。この停止は公式ランク上の通常の敗北判定と混同せず、運営上の失敗として扱う規則を別に設ける。

## 4. 戦闘エンジンの関数的境界

概念上の契約は次のとおり。実際のRust API・型名・シリアライズ形式は未確定。

    Enbu.simulate(
      attacker: ValidatedCombatantSnapshot,
      defender: ValidatedCombatantSnapshot,
      rules: VerifiedSenritsu,
      context: ImmutableMatchContext
    ) -> SimulationArtifact

`ValidatedCombatantSnapshot`には兵科、兵数、配置、設備、初期戦術メモリ、および検証済み・バージョン付きの戦術プログラムを含む。`ImmutableMatchContext`には戦場、ルールセット、エンジン版、CUスケジュール版、終局条件を含む。

戻り値は概念的に以下へ分かれる。

- `MatchResult`：勝敗、終局理由、終局Tick、確定統計、CUなどの結果。
- `PresentationReplay`：許可された画面描画に必要な戦場の状態差分・イベント。プレイヤーの戦術コードやIRを含めない。
- `RestrictedDiagnostics`：条件評価、内部命令、状態変数、CU詳細などの内部診断。信頼境界外へそのまま返さない。

これは**1試合についての純粋な決定論的計算**を表す。実行中は多数のTickと戦闘状態を持つが、試合が終わるまで対人入力を待たず、サービス全体に戦闘状態を常駐永続化する必要はない。同じ入力・バージョンでは同じ論理結果を返す。

## 5. 描画と情報秘匿

レンダラーは`PresentationReplay`を受け取り描画するだけであり（表示スキーマ・時間・座標の契約は [REPLAY.md](REPLAY.md)）、勝敗確定計算を担当しない。補間・描画速度・見た目の変更は結果に影響しない。

将来の公式戦では、攻撃側・防衛側の非公開戦術IRをサーバー内で保持し、相手クライアントへ渡さない。サーバーは別の**許可リスト方式の公開リプレイ生成処理**を持ち、内部トレースから任意項目を後から削除するだけの方式にしない。

- 公開可能：戦場で観測できた出撃、移動、交戦、HP変化、施設破壊、勝敗など。
- 非公開：対戦相手のソース、IR、未発火ルール、状態メモリ、条件判定、内部CU詳細。
- 自軍の診断情報は認可された所有者へ限定して提供する。運営用の完全トレースは別の信頼領域で扱う。
- 公開リプレイの戦場イベントを繰り返し観測して戦術を推定すること自体は防ぎ切れない。完全な秘匿性を保証しない。

エンジンの内部監査・再実行には両戦術およびルールの不変スナップショットが必要。**結果ハッシュや公開リプレイだけから完全再計算することは求めない**。

## 6. ポータビリティと将来のジョブモデル

Rustの同一コアから、ローカルブラウザ用のWASM版と、ヘッドレス検証や将来の公式戦用のネイティブ版を作る。ブラウザ版はWeb Worker上で実行する方向。ネイティブ版とWASM版で結果・CUが一致するようにゴールデンテストを実施する。

将来の公式戦では、両者の確定入力から結果が数学的に一意になる。ただし**ランク反映用の正式な確定**には、サーバーでの再検証、権威実行、冪等な記録処理が必要。

公式戦計算は単位ジョブ化できる。サーバーの役割を対戦受付・スナップショット確定・ジョブ調停・結果精算と分離し、戦闘状態は各ワーカー内で一時的に保持する。**ネイティブRust常駐ワーカー／ワーカープールを第一候補**とし、WASMインスタンスを複数起動する方式やCloudflare Workers上の実行との比較は、性能・実行制限・隔離要件を測定してから判断する。計算基盤の選択はゲーム意味論とCU契約を変えない。

## 7. 受入時に証明する性質

- GUIとテキストの等価戦術は同じ意味的結果・CUを返す。
- 同一入力のネイティブ版とWASM版は勝敗・確定統計・CU・論理トレースが一致する。
- 物理最適化をオン・オフしても結果・論理CU・公開用イベントが同一。
- 無効な型、アクセス範囲外の戦術、超過入力やバージョン不一致は拒否する。
- ブラウザ描画は相手の非公開戦術を必要としない。
- 公開リプレイ形式にソース、IR、秘密変数、内部CUトレースが混入しないことを検査する。
- 同一公式戦ジョブの再試行・重複応答でチケット・レートが二重変更されない（将来のオンライン実装時）。
