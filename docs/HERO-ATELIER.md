# Hero Atelier — G2統合アートディレクションと専用画面

## 位置づけ

本書は [GRAPHICS.md](GRAPHICS.md) の戦場表現と [UI-DESIGN.md](UI-DESIGN.md) の画面体験をつなぐ**G2向けデザイン正本**。Heroの造形、Hero Collection / Detail / Skill Tree / Squad Assembly、戦場との画風の一貫性を定義する。戦闘ルールは [UNITS.md](UNITS.md) と [COMBAT.md](COMBAT.md) が優先する。

目標は「AAA級のキャラクター展示とビルド構築の手触り」を、ブラウザ・コード生成主体の制作制約の下で目指すこと。**写実的なAAAモデルを12体完成済みとみなさない**。既存G1の小型ジオラマも、直前の写実寄りHeroモックも、そのまま最終品質の正本にはしない。

## 1. デザインテーゼ

**Stylized 3D Tactical Fantasy**。Heroを大きく見ると装備・材質・表情・動作が魅力的で、戦場の俯瞰では同じHeroが明瞭なシルエットで識別できる。

- 戦場は戦線と観測の読みやすさ、Hero Atelierはキャラクターの存在感と戦術設計を優先する。
- **同一のHero identity、装備形状、材質体系、色・エンブレム、アニメーション意味論を両画面で共有**する。Hero Detailだけ別人の写実イラストにしない。
- 近景は高品質なStylized 3D、遠景は同一モデル系列のLOD・簡略表現。Pixel 3Dは任意のレンダーパスであり、Smooth 3Dも正式な比較対象。
- 金属・革・布・石材・魔法光の質感は一貫したPBR／トゥーン寄りの材質規則で作る。高解像度の写実的な皮膚と極端に簡素な箱形の戦場モデルの混在を避ける。
- Heroの個性はシルエット、武器、姿勢、アニメーション、固有色で表現する。単に12体を色違いにしない。
- 画面を豪華にするための装飾より、Hero選択・Skill Tree・Squad構築の理解と操作を優先する。

## 2. 視覚システム

| 要素 | 共通ルール |
| --- | --- |
| 背景 | 深いスレート／群青のUIと、石造・金属・自然環境の3Dステージ |
| 強調 | 青／シアンは味方、朱色は敵、琥珀／淡い金は選択・成長・能力の強調。金は全画面へ乱用しない |
| キャラクター | やや誇張した頭身・装備・武器、シルエット優先のStylized 3D |
| 材質 | 鎧・布・革・肌・木・魔法のマテリアル規則を共有し、Heroごとに逸脱しない |
| タイポグラフィ | 日英併記可能な読みやすい本文。Hero名は大きく、技術値とTickは等幅数字 |
| Icon | スキルは能力カテゴリと固有エフェクトを識別できる。意味不明な装飾アイコンを量産しない |
| Motion | キャラクター変更、カメラ寄り、スキルプレビュー、ノード選択の意味を伝える短い遷移 |
| Lighting | Hero展示用のkey/fill/rim、戦場用の環境光・方向光。光の演出が所属色・輪郭を消さない |

UIの操作系は高解像度で描画する。戦場Pixel 3D処理をHeroの顔やスキルツリーの文字へ強制しない。アクセシビリティ、コントラスト、フォーカス、reduced-motionを維持する。

## 3. 4つの専用画面

### Hero Collection

**目的：12体の違いを一目で理解し、5体の戦型へ選択する。**

- 前衛6／後衛6、配置適性・戦闘特性・戦術特性でフィルターする。
- 12体を単なるアイコン一覧にせず、統一したカメラ・照明・画角のポートレート／モデルプレビューで見せる。
- 選択中Heroは大きく強調。役割・3軸属性・主な能力とSolo／Squad適性を確認できる。
- 編成枠は常に「5枠中いくつ選択したか」を実状態から示す。重複選択の可否はSenritsuの実ルールに従う。
- 初期の固有名・スキル名はCatalogが未確定なら仮名として表示し、実装済みと偽らない。

### Hero Detail

**目的：Heroを理解し、ビルド設計へ進む。**

- Desktopは画面の主領域に大きな3D Heroを配置し、右に3軸属性・基礎ステータス・能力・戦術上の強みを置く。
- モデル回転、待機・移動・通常攻撃・スキル演出のプレビューを用意。表示不能なアニメーションは有効なボタンにしない。
- Hero固有の能力と、Jinreiから使用可能になるCapabilityを分けて説明する。
- ステータスはCatalog由来の値だけを表示し、架空のレーダーチャート数値を実性能として出さない。
- Hero Detailのために戦場と異なるHeroモデルの真実を二重管理しない。

### Skill Tree

**目的：戦闘前に、レベルアップ時の取得経路を構築する。**

- Heroの3Dプレビューは縮小し、分岐ノードを持つSkill Treeキャンバスを主役にする。
- ノードは取得条件、レベル、前提、効果、発動条件、Cooldown、Jinrei Capabilityとの関連を表示する。
- 現在選択した経路と、未選択・未解放・選択不能・依存不成立を区別する。
- 選択するとレベルごとの予定取得、能力変化、使用可能なJinrei操作をプレビューする。
- 実際の取得は試合中のレベルアップに従う。編集時の「予定」を「取得済み」と表示しない。
- 変更・取消・プリセット切替は一貫したドラフト状態を持ち、戦型保存時にSenritsuで検証する。

### Squad Assembly

**目的：選択した5HeroをSquadへ分割し、陣形とJinreiの運用を設計する。**

- 5体のHero一覧、Squadグループ、3D隊列プレビューを表示。
- Solo / Duo / Trio / Quartet / Quintetを含む合法な人数分割を支援する。
- Squadの人数別移動倍率と連携成熟の特性を**Catalog/Senritsuの実値**から表示する。
- 3Dプレビューでは前衛／後衛の位置関係を確認できるが、戦闘中の自動分離・合流はJinreiの指示によることを明示する。
- 初期編成と戦闘中のJinreiによる再編成は別概念。試合中に画面操作でHeroを動かす機能にしない。
- 変更した構成は同じ戦型のドラフトを更新し、Hero DetailやSkill Treeとの状態が食い違わない。

## 4. 画面構成と遷移

Desktopでは「Hero Collection → Hero Detail → Skill Tree → Squad Assembly → 戦型／Jinrei → 演武」の導線を持つ。**この導線は自由編成の代表ルートであり、必ずすべての詳細画面を通る順序強制ではない**。Quick Startや保存からの復帰・個別修正・Readyへの直接復帰の全遷移は [PRE-BATTLE-FLOWS.md](PRE-BATTLE-FLOWS.md)、画面別契約は [PRE-BATTLE-SCREENS.md](PRE-BATTLE-SCREENS.md) を正本とする。Detailはキャラクターを中心に、Skill Treeはキャンバスを中心に、Assemblyは5体の関係を中心に**それぞれ異なる情報階層**で設計する。

MobileはDesktopの縮小版にしない。
- Collection：縦長のHeroカード／一覧、属性フィルター、5体選択の固定導線。
- Detail：モデルを大きく見せる独立画面、ステータスはスクロール領域。
- Skill Tree：独立したパン／ズーム可能な画面、選択ノード詳細はボトムシート。ピンチ必須にはしない。
- Squad Assembly：Hero選択→所属Squad→隊列プレビューの順に段階化し、ドラッグ以外の操作も用意する。
- キーボード、IME、Safe Area、長い日本語、画面回転、戻る操作で編集状態を失わない。

全ビューは**同一の戦型ドラフトとCatalogを参照**し、画面間で独立した偽データを持たない。Heroの選択変更がSkill TreeやSquadに与える影響は検証・差分表示し、黙って設定を捨てない。

## 5. 3Dアセット制作契約

- Hero Catalogの `appearanceKey` と、表示専用のアセットmanifestを接続する。戦闘計算はメッシュ・マテリアル・アニメーションに依存しない。
- 12Heroは前衛／後衛の役割を反映した独自の輪郭・武器・装備・立ち姿を持つ。F01–F06/R01–R06の設計上の役割と照合する。
- 共通の骨格・リグ・装備パーツ・材質ライブラリを優先し、Heroごとに完全な別実装を増やさない。
- 最低限、Hero Detail用の高品質モデルと戦場用のLODを同じidentityから生成／派生する。
- アセットの生成元、generator version、assetKey、LOD、材質、アニメーション、ライセンス／出典を管理する。
- Three.jsのプロシージャル生成を第一手段にし、必要に応じてBlender PythonでGLBを生成する。Codexだけで写実的AAA級の品質を保証するという前提を置かない。
- 未許諾のゲームアセット、他作品のキャラクター画像、権利不明の素材を本番アセットへ混入しない。

## 6. 検証と受入

1. Hero Collectionで12Heroの輪郭と役割が識別できる。5体選択がCatalog制約と一致する。
2. Hero Detailの大きな3Dモデルと戦場LODが同じHeroとして認識できる。モデルの回転・アニメーションが実動作する。
3. Skill Treeの分岐選択・前提条件・レベル取得予定・Jinrei Capabilityが一致し、無効経路を検出できる。
4. Squad Assemblyの5Hero所属が一意で、編成と速度倍率・隊列プレビューが一致する。
5. Desktop 1440×900／1920×1080、Mobile 390×844／430×932、狭幅320pxで実ブラウザ表示を確認する。
6. 戦場とHero Detailの比較スクリーンショットで、材質・配色・装備・輪郭が一貫していることを目視確認する。
7. 初期、選択、変更中、未保存、検証エラー、GPU非対応、戻る／復帰の状態を操作確認する。
8. 描画FPS低下やLOD切替が戦闘結果・Replay・CUを変えないことを確認する。
9. スクリーンショットの存在・ビルド成功だけでAAA品質達成とは報告しない。美観と操作、契約の検証を分ける。

## 7. G2への位置づけ

本書はG2のアート基盤をHero画面と戦場へ**共通適用**する追加契約。G1のReplay／Enbu境界は維持する。現在別セッションで進む大規模Senritsu実装と同時に本書の全UIを完成させたとみなさず、既存実装の進捗と競合を確認して統合する。

画像生成モックは**デザイン参考**であり、実在するHeroの確定名、能力値、アセット、画面の完成証拠ではない。直前の写実寄りモックをそのままコピーするのではなく、同じHeroがDetailと戦場でつながるStylized 3Dの統一感を優先する。
