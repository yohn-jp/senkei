# 実装順序・受入条件・未決定仕様

## 1. フェーズ境界（確定）

最優先目標は、サーバー・認証・公式ランク戦なしで遊べる**完全ローカルのPvE戦術開発ゲーム**です。オンライン機能を先行して開発しません。

### Phase A — Core battle

- 初期Senritsuとして3レーン・軍備・施設・戦況の最小ルールを定義し、Enbuで実行する。
- 固定された二つの戦術による自動戦闘が終了する。
- 同じ入力で、繰り返し同じ結果になることをテスト。
- 外部時刻・乱数・非安定な順序に依存しない。

受入条件：ネイティブのヘッドレス戦闘を同じ入力で繰り返し、結果・状態・終局を再現できること。

### Phase B — Tactics language & CU

- Jinreiのテキスト入力、パース、型検査、Typed IR、Costed Logical IR、専用バイトコード、Rust製VMを実装。
- 指定された有限命令の実行、複合条件、状態変数、CU課金と上限を検証。
- ベクトル／行列指向の戦術表現を同じルールに従って実装。
- 不正戦術・過大入力を拒否する。

受入条件：戦術変更で戦況に差が生じ、同一IRを何度実行しても命令・CUが一致すること。CU固定後の物理最適化をオン／オフしても論理CU・命令・結果が一致すること。

### Phase C — Browser developer experience

- Rust製VM・戦闘エンジンのWASMアダプター、Web Worker、戦術／配置編集、リプレイ、デバッグを実装。
- ノーコードから生成したIRとコードから生成したIRが同じ意味論を持つことを確認。
- IndexedDBで保存・復元、戦術の版管理・インポート／エクスポート。
- UIが固まらずにNPC戦・複数ケースのベンチマークを実行する。

受入条件：サーバーAPIなしでブラウザ内の編集→PvE→分析→修正→再戦が完結すること。描画処理とシミュレーションが独立し、描画はイベントのみを再生できること。

### Phase D — Playable local product

- 初心者向けプリセット、NPCキャンペーン、難易度・課題・回帰ケースを整備。
- プレイヤーが敗因を把握できるリプレイ・命令トレース・CU表示を提供。
- 新規ユーザーがコード記述なしで初戦を開始できる。
- 静的配信後、必要な素材がキャッシュされればオフラインで主要機能が利用できることを検証。

受入条件：ローカルで無制限のPvE、戦術編集、回帰テストが操作でき、公式戦への接続を要求しないこと。

### Phase E — Future online competitive platform

**別スコープ。** 公式非同期PvP、チケット、レート、ユーザー管理、サーバー権威戦闘はローカル版が成立してから設計・実装します。初期の受入条件には入れません。

## 2. 仕様未確定（次の検討で決める）

最初の議題は**Jinrei（陣令）の語彙・文法・型体系**です。次に各命令の意味、CUコスト、Tickの処理順序とゲームバランスを確定します。

- DSLの構文、予約語、優先順位、文法の表現方式。
- 型システムと集約／行列の意味論、GUIとの相互編集モデル。
- 読める戦場データ、出せる命令の有限集合。
- 兵科・施設・生産、レーン間移動、戦闘ルールの具体仕様。
- CU料金表・資源配分・上限超過時の動作。
- Tick幅、攻守同時解決、射程・衝突、勝敗の同点・時間切れ。
- 保存・エクスポートの具体スキーマ。
- リプレイ可視化と大規模ベンチマークの負荷基準。
- 将来の公式戦のレーティング計算とチケット制度。

## 3. 開始前に守るべき不変条件

1. コアはCloudflare、React、ブラウザのAPIに依存しない。
2. 戦闘結果とゲームCUはホスト性能やJavaScript実行時間で変化しない。
3. ノーコード／テキストのどちらも同じ構造化IR・戦闘能力を持つ。
4. テスト・PvEの実行にオンラインサービス・チケットを要求しない。
5. 戦術プログラムに任意のホストコード実行権限を与えない。
6. 誤動作・敗因を戦闘ログ、状態、命令、CUから検証できる。
7. 決定事項と未決事項を混同せず、次の設計議論に残す。

## 4. リリース・OSS方針

- コアロジック、DSL、戦術VM、デバッガ、NPCをOSSとして公開する方向。
- 既存のLICENSEはApache-2.0。変更しない。
- 将来のロゴ、名称、素材の利用条件は別途規定する。
- ドキュメントに日付付きの「現状」を埋め込まず、Git履歴で追う。

## 5. 追加の実行契約

コンパイル、CUの論理／物理分離、戦闘の単位ジョブ、結果とリプレイの境界は [EXECUTION.md](EXECUTION.md) を参照してください。将来の公式戦では非公開IRをクライアントへ送らず、公開リプレイのスキーマ検査と重複精算防止を受入条件に追加します。

## 6. コンポーネント別の実装証明

- Senkeiモデル: 不変戦型スナップショットが対象SenritsuダイジェストとJinreiの版を参照できる。
- Senritsu: 3レーンの最初のパッケージを検証・正規化し、型／観測／Capability／CU定義を公開できる。
- Jinrei: Senritsuスキーマを元に不正命令をコンパイル時に拒否し、同じ戦場入力で同じIntent・CUを返す。
- Enbu: 2つのSenkeiとSenritsuから戦闘結果と再生イベントを出し、戦闘ルールの具体数値や兵科名をコアへハードコードしない。
- 全体: 新しい兵科等のデータ拡張と、物理意味論が必要な拡張を区別した互換性テストを持つ。

責務境界の正本は [COMPONENTS.md](COMPONENTS.md)。
