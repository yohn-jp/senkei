# 実装順序・受入条件・未決定仕様

## 1. フェーズ境界（確定）

最優先目標は、サーバー・認証・公式ランク戦なしで遊べる**完全ローカルのPvE戦術開発ゲーム**です。オンライン機能を先行して開発しません。

### Phase A — Core battle

- 3レーン・軍備・施設・戦況の最小ドメインを実装。
- 固定された二つの戦術による自動戦闘が終了する。
- 同じ入力で、繰り返し同じ結果になることをテスト。
- 外部時刻・乱数・非安定な順序に依存しない。

受入条件：ネイティブのヘッドレス戦闘を同じ入力で繰り返し、結果・状態・終局を再現できること。

### Phase B — Tactics language & CU

- テキスト入力、パース、型検査、共通Typed IR、VMを実装。
- 指定された有限命令の実行、複合条件、状態変数、CU課金と上限を検証。
- ベクトル／行列指向の戦術表現を同じルールに従って実装。
- 不正戦術・過大入力を拒否する。

受入条件：戦術変更で戦況に差が生じ、同一IRを何度実行しても命令・CUが一致すること。

### Phase C — Browser developer experience

- WASMアダプター、Web Worker、戦術／配置編集、リプレイ、デバッグを実装。
- ノーコードから生成したIRとコードから生成したIRが同じ意味論を持つことを確認。
- IndexedDBで保存・復元、戦術の版管理・インポート／エクスポート。
- UIが固まらずにNPC戦・複数ケースのベンチマークを実行する。

受入条件：サーバーAPIなしでブラウザ内の編集→PvE→分析→修正→再戦が完結すること。

### Phase D — Playable local product

- 初心者向けプリセット、NPCキャンペーン、難易度・課題・回帰ケースを整備。
- プレイヤーが敗因を把握できるリプレイ・命令トレース・CU表示を提供。
- 新規ユーザーがコード記述なしで初戦を開始できる。
- 静的配信後、必要な素材がキャッシュされればオフラインで主要機能が利用できることを検証。

受入条件：ローカルで無制限のPvE、戦術編集、回帰テストが操作でき、公式戦への接続を要求しないこと。

### Phase E — Future online competitive platform

**別スコープ。** 公式非同期PvP、チケット、レート、ユーザー管理、サーバー権威戦闘はローカル版が成立してから設計・実装します。初期の受入条件には入れません。

## 2. 仕様未確定（次の検討で決める）

最初の議題は**戦術DSLの語彙・文法・型体系**です。次に各命令の意味、CUコスト、Tickの処理順序とゲームバランスを確定します。

- DSLの構文、予約語、優先順位、文法の表現方式。
- 型システムと集約／行列の意味論、GUIとの相互編集モデル。
- 読める戦場データ、出せる命令の有限集合。
- 兵科・施設・生産、レーン間移動、戦闘ルールの具体仕様。
- CU料金表・資源配分・上限超過時の動作。
- Tick幅、攻守同時解決、射程・衝突、勝敗の同点・時間切れ。
- 保存・エクスポートの具体スキーマ。
- リプレイ可視化と大規模ベンチマークの負荷基準。
- 将来の公式戦のレーティング計算とチケット制度。

## 3. 開始前に守るべき不変条件

1. コアはCloudflare、React、ブラウザのAPIに依存しない。
2. 戦闘結果とゲームCUはホスト性能やJavaScript実行時間で変化しない。
3. ノーコード／テキストのどちらも同じ構造化IR・戦闘能力を持つ。
4. テスト・PvEの実行にオンラインサービス・チケットを要求しない。
5. 戦術プログラムに任意のホストコード実行権限を与えない。
6. 誤動作・敗因を戦闘ログ、状態、命令、CUから検証できる。
7. 決定事項と未決事項を混同せず、次の設計議論に残す。
